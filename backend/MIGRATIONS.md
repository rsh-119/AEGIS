# Database migrations & seeding

Aegis uses [Alembic](https://alembic.sqlalchemy.org/) to version the Postgres
schema, and a small seed script (`app/db/seed.py`) to populate a local dev
database with realistic test data. This replaced a hand-maintained list of
raw `ALTER TABLE ... IF NOT EXISTS` strings that used to live in
`app/core/database.py`'s `init_db()` — no version tracking, no rollback,
and (found while migrating) had actually drifted from what the ORM models
in `app/models.py` declare. See `alembic/versions/4f57afa92297_baseline.py`
for the full account of what that drift was and how it was reconciled.

## How schema changes get applied

`init_db()` (`app/core/database.py`) runs `alembic upgrade head`
automatically on every backend startup — same as the old raw-SQL list did.
Upgrading a database that's already at head is a no-op, so this is safe
under multi-worker startup (`--workers 2` in production). You don't need to
run anything manually for the app itself to pick up new migrations; this
only matters when you're the one *writing* a migration.

## Workflow for a schema change

1. Change the model in `app/models.py`.
2. Generate a migration:
   ```bash
   cd backend
   alembic revision --autogenerate -m "add foo column to bar"
   ```
3. **Read the generated file in `alembic/versions/`** — autogenerate is a
   starting point, not ground truth. It won't detect everything (e.g. plain
   column renames look like a drop + add; check constraints; some type
   changes) and won't infer any data backfill you need. Hand-edit as needed.
4. Apply it locally: `alembic upgrade head`
5. Verify: `alembic check` should report no further diff between the DB and
   the models. `alembic current` shows what revision the DB is on.
6. Commit the migration file along with the model change, in the same PR.

Rollback one revision: `alembic downgrade -1`. Every autogenerated migration
gets a `downgrade()` — review it same as `upgrade()`, autogenerate's
downgrade is a best-effort inverse, not guaranteed correct for every op type
(data-loss ops like column drops aren't reversible by definition; the
downgrade will restore the column but not the data that was in it).

## Seeding a local dev database

```bash
cd backend
python -m app.db.seed              # idempotent — safe to re-run
python -m app.db.seed --reset      # wipe the 6 app tables first, then seed
python -m app.db.seed --extra-users 5   # more than the default 3 fake users
```

Creates one known-credential dev login (`devtest@aegis.local` /
`DevTest123!`, admin + Pro) with sample holdings/watchlist/a price
alert/an AI-cache entry/a portfolio review, plus a few additional
Faker-generated users for exercising multi-user flows (e.g. the `/admin`
dashboard's user list, or watchlist's per-user uniqueness constraint).

Refuses to run unless `APP_ENV=development` — this is the only guard, and
it's a hard requirement: never point this at a staging/production
`DATABASE_URL`. `faker` is a dev-only dependency
(`backend/requirements-dev.txt`, not installed in the production Docker
image) — `pip install -r requirements-dev.txt` to get it locally.

## Zero-downtime schema changes (Expand → Contract)

For anything beyond a purely additive nullable column, split the change
across multiple deploys instead of one migration that both changes the
shape and requires the app to already know about it:

1. **Expand** — add the new column/table nullable, or with a server
   default. Never `NOT NULL` in the same migration that introduces it — old
   app code is still running against this schema until the next deploy.
2. **Dual-write** — deploy app code that writes both the old and new shape.
   Old readers keep working unmodified.
3. **Backfill** — a data migration (separate from the DDL migration, and
   batched if the table is large) populates the new column/table for
   existing rows.
4. **Cut over reads** — deploy app code that reads the new shape. Verify in
   production before proceeding.
5. **Contract** — only once step 4 is confirmed stable, a follow-up
   migration drops the old column/constraint, and adds `NOT NULL` now if
   the new column needed it.

Each step is its own Alembic revision — small and independently
reversible. This is the formalized version of the pattern the pre-Alembic
`ALTER TABLE ... IF NOT EXISTS` list was already reaching for informally
(e.g. adding `holdings.user_id`/`watchlist.user_id` as nullable, "existing
rows keep NULL = legacy"), just now with actual rollback support instead of
one-way idempotent strings.

## Local Postgres ports (context for the confusing history)

- `docker-compose.yml`'s `db` service now publishes to host port **`5434`**
  (container-internal `5432`, unaffected). This is what local dev should
  point `DATABASE_URL` at.
- Port `5433` was a **native (non-Docker) Postgres install** on some
  development machines, predating the Docker setup, holding the "real" data
  until it was migrated onto the `5434` container (full `pg_dump`/verify/
  cutover — see git history around the port-migration commits). It's being
  decommissioned; nothing in the app should reference `5433` anymore.
